# 01 - 章介绍

假设：现在凌晨两点，线上突然收到一条告警：

> `payment-service` 从 15:10 开始出现大量支付失败。请检查服务状态、监控指标、错误日志和最近发布记录，找出最可能的故障原因并给出处理方案。未经确认，不允许重启服务或者回滚版本。
>

看到这个任务，咱们肯定会骂娘。

但是，大家觉得：**Agent 会先做什么？**

这个问题并没有唯一答案。

它可以先检查服务是不是还活着，也可以先看支付失败率从什么时候开始上涨的。

如果日志里出现数据库连接超时，可能还要继续检查连接池。

不同工具返回不同的结果，可能会把任务带向完全不同的方向。

所以，大家看，这种任务就不是提前写几个固定步骤可以轻松解决的了。

那么这种问题，怎么办呢？

这就是第四章要研究的东西。

## 这一章会实现什么
这一章会一直围绕前面的线上故障任务来讲。

为了让所有同学都可以得到相同的运行结果，咱们会提供一套本地故障数据模拟器。

它可以返回服务状态、监控指标、错误日志、数据库连接池和发布记录，也会模拟工具超时、错误结果以及高风险操作。

咱们先从 `ReAct` 开始。

> **注意**，这玩意不是 `React`，是 `ReAct` 。他不是一个框架，而是一种思想
>

先让 Agent 执行一个动作，读取一次真实结果，再根据这个结果决定下一步。

这条链路跑通以后，再加入任务规划。

Agent 需要知道当前有哪些步骤，哪些已经完成，哪些还在等待。

如果新的证据推翻了原来的判断，还要保留已经确认过的信息，重新安排后面的计划。

然后，咱们继续处理工具。

工具接入得再多，如果名称和描述写得不清楚，模型依然可能出错。

最后，再讲 Agent 的执行控制和失败恢复。

应用程序会记录任务状态、工具调用次数、执行时间和停止原因。

工具失败以后，要判断应该重试、切换备用路线、重新规划，还是把任务交给人工。

任务结束以前，还要检查结论是否真的有证据支持。

最后，咱们还会考虑实现一个完整的线上故障排查 Agent。

到时候，大家可以在页面中看到 Agent 当前的任务计划、每一次工具调用、工具返回结果、计划变化、错误恢复、人工确认以及最终停止原因。
